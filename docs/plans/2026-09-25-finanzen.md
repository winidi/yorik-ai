# Plan: Finanzen (Bankkonten-App) — Umsätze lesend, mehrere Konten, geteilt oder privat

Stand 2026-09-25. Auslöser: Dirk hat die FinTS-Produktregistrierung bei
der DK abgeschickt und will jetzt echte Kontoumsätze (Sparkasse, ING)
in Yorik sehen können — read-only, kein Überweisen. Perspektivisch
Kategorisierung, wiederkehrende Zahlungen, Prognose (siehe „Später").

## Bestandsaufnahme — was schon da ist

- **`backend/connectors/banking_fints.py`** — fertiger, funktionierender
  Read-only-FinTS-Connector (Operationen `accounts`/`balance`/
  `transactions`) über die `fints`-Bibliothek (bereits in `venv`
  installiert, Version 5.0.0). Nutzt `FinTS3PinTanClient`.
- **`backend/credential_store.py`** — Fernet-verschlüsselte
  Zugangsdaten-Ablage, nennt „banking-fints“ explizit als Beispiel im
  eigenen Docstring.
- **Aber:** Der bestehende Connector ist **ein einziger globaler Slot**
  (`credential_store.get("banking-fints")`, ein fester Name, kein
  `owner_user_id`, kein Konzept „mehrere Konten“). Passt für „Admin hat
  ein Konto“, nicht für „Dirk hat Sparkasse+ING privat, dazu ein
  gemeinsames Konto mit Beate“. Der Connector-Code (FinTS-Aufrufe,
  Serialisierung) ist trotzdem die richtige Referenz/Bibliothek — nur
  die Speicherung muss wie bei `email_accounts` werden: eine Zeile pro
  Konto, `credential_key` zeigt in den `credential_store`.
- **Sichtbarkeitsmodell existiert schon** (`backend/spaces.py`,
  `row_filter`): eine Zeile gehört ihrem Owner, ist in dessen Space
  sichtbar, kann pro Zeile geteilt werden. Genau das braucht „meine
  Konten privat, gemeinsames Konto für beide“ — persönliches Konto im
  privaten Space des Owners, gemeinsames Konto im Shared-Space oder mit
  `row_shares`-Zeilen für beide.
- **Migrationen:** aktueller Stand `161_address_suggestions_per_person.sql`
  → nächste Nummer `162`.
- **Kein bestehender Finanz-Plan** in `docs/plans/` — das hier ist der
  erste.

## Ziel (dieser Durchlauf)

1. Mehrere Bankkonten pro Nutzer verbinden (Sparkasse, ING, beliebig
   viele), PIN-Eingabe nur direkt im Browser des Nutzers, nie über den
   Chat oder mich.
2. Sichtbarkeit wie beim Rest von Yorik: eigenes Konto sieht nur der
   Owner; ein Konto kann als „Shared“ angelegt werden, dann sehen es
   alle im Haushalt (z. B. Dirk + Beate gemeinsames Konto).
3. Umsätze werden synchronisiert und lokal gespeichert (nicht bei
   jeder Chat-Frage live gegen die Bank gefragt — TAN-Reibung,
   Geschwindigkeit).
4. Chat kann Fragen dazu beantworten („was hab ich für Lebensmittel
   ausgegeben“) über Skills, die auf den gespeicherten Umsätzen
   arbeiten.
5. Eine echte Seite (App) in Yorik: Konto verbinden, Kontostand,
   Umsatzliste, nach Kategorie filtern.

## Regeln (Sicherheit zuerst)

- **PIN nie im Chat, nie bei mir.** Eingabe ausschließlich über ein
  echtes Formular im Browser des Nutzers, das direkt an die API
  sendet — gleiches Muster wie beim E-Mail-Konto-Setup
  (`POST /api/email/accounts`). Ich baue das Formular, tippe aber
  niemals selbst Zugangsdaten hinein.
- **Sichtbarkeit:** `owner_user_id` + `visibility` (`private` default,
  `shared` für Haushaltskonten) auf `bank_accounts`; `bank_transactions`
  erbt die Sichtbarkeit ihres Kontos. Kein Admin-Ausnahme-Zugriff auf
  private Konten fremder Personen (gleiche Regel wie bei Recordings).
- **Nur lesend.** Keine Überweisungs-Funktion, nirgends — auch nicht
  als spätere Ausbaustufe ohne explizite neue Entscheidung.
- **Sync, kein Live-Abruf pro Chat-Frage.** TAN-Reibung vermeiden;
  Skills lesen die lokale Tabelle, ein Hintergrund-Job synchronisiert
  periodisch (`backend/workers.py`-Muster).

**Design-Review der Inspirationen (bevor gebaut wird):**
- Bild 1 (Mobile, lila Verlaufskarte + Vertragsliste + bunte
  Budget-Kreis-Icons unten): der lila Gradient-Hero + die
  Icon-in-Kreis-Badges sind genau der generische Fintech-App-Kit-Look.
  Übernommen wird nur die INFORMATION (Vertragsliste, "Konten auf
  einen Blick"), nicht die Bausteine.
- Bild 2 (Desktop "Finexy"): bunte Stat-Kacheln, Header komplett ohne
  Luft nach oben (Titel klebt am Fensterrand) — das ist der Punkt, den
  Dirk zurecht kritisiert hat ("oben garkeinen Platz gelassen"). Wird
  im neuen Layout bewusst vermieden: Konto-Umschalter + Hero bekommen
  eigenen Atem-Abstand unter der Tab-Leiste, keine Inhalte kleben am
  oberen Rand.
- Yoriks eigene, in Runde 1 etablierte Sprache wird fortgeführt statt
  neu erfunden: schmaler Farbrand statt Icon-Badge, Haarlinien statt
  Schatten-Karten, tabular-nums, emerald/rose für +/-. Neu dazu: amber
  als eigener Akzent NUR für Verträge/Abos (visuell klar getrennt von
  Einnahmen/Ausgaben-Grün/Rot).

**Layout-Plan:**
- Neue Tab-Leiste unter dem Header: Übersicht (neuer Default) / Konten
  / Umsätze / Verträge. Unterstrich-Tabs, keine Pill-Buttons.
- Konto-Umschalter direkt darunter als horizontale Chip-Reihe: "Alle
  Konten" + ein Chip pro Konto; gewählter Chip = gefüllter Hintergrund.
  Eigener Abstand nach oben UND unten (behebt die "kein Platz"-Kritik).
- Übersicht-Tab, von oben nach unten:
  1. Ein großer Hero-Betrag (Netto-Saldo der Periode) — der EINE
     mutige Moment der Seite, alles andere bleibt ruhig/flach.
  2. Zwei-Spalten-Quickstats, durch Haarlinie getrennt, konfigurierbar:
     Default "Lebensmittel diesen Monat" + "Verträge & Abos diesen
     Monat"; per kleinem Stift-Icon gegen andere Kategorien tauschbar
     (persistiert serverseitig, siehe unten) — das macht "konfigurierbar"
     konkret, ohne ein volles Drag&Drop-Widget-System zu bauen.
  3. Vorschau-Liste "Verträge & Abos" (erkannte wiederkehrende
     Zahlungen), gleiche Zeilen-Bauweise wie die bestehende
     Kontoliste (Haarlinie + Farbrand), kein Icon-Kreis.
- Konten/Umsätze-Tabs: heutiger Inhalt fast unverändert, nur hinter
  Tabs statt permanent auf einer langen Seite.
- Verträge-Tab: volle Liste aller erkannten wiederkehrenden Posten
  (Kategorie, letzter Betrag, wie oft in den letzten 6 Monaten gesehen).
- Ab `lg:`-Breakpoint zweispaltiges Layout (Übersicht/aktiver Tab links,
  Verträge+Konten-Sidebar dauerhaft rechts) — erfüllt "auf dem Desktop
  mehr Infos", ohne die Mobile-Ansicht zu verändern.

**Technik-Plan (keine neue DB-Migration nötig):**
- Wiederkehrende Zahlungen: rein berechnet aus `bank_transactions`
  (Gruppierung nach Konto+normalisiertem Gegenkonto+Kategorie, Betrag
  innerhalb ±5% über ≥2 verschiedene Kalendermonate der letzten 6
  Monate) — neuer Endpoint `GET /api/bank/recurring`, keine neue
  Tabelle.
- KI-Kategorisierung: Keyword-Tabelle bleibt als schnelle erste Stufe
  (kostenlos, deterministisch). Alles, was NICHT matcht, geht als EIN
  Batch-Call an die lokale KI (`os.getenv("HOMEOS_MODEL",
  "qwen3.8-27b")` über `os.getenv("HOMEOS_LLM_BASE_URL",
  "http://127.0.0.1:8080/v1")`, exakt das Modell, das Yoriks eigener
  Chat auf der Workstation nutzt — read via env, nie hart codiert),
  strict JSON, temperature 0 — gleiches Muster wie
  `fill_pdf_form/skill.py`s Feld-Mapping-Call. Läuft in
  `bank_sync.sync_account`, nur für neu eingefügte, noch
  unkategorisierte Zeilen dieses Syncs; einmaliges Backfill-Skript für
  die schon vorhandene Historie.
- Konto-Umschalter: reiner Frontend-State + vorhandener
  `account_id`-Filter auf `/api/bank/transactions` (schon da) — kein
  Backend-Änderung nötig.
- Fokus-Kategorien: `app_settings`-Tabelle (gleiches Muster wie
  `prepare_email`s Draft-Storage), Key `finance_focus_categories_<user_id>`,
  neue kleine Endpoints `GET/PUT /api/bank/focus-categories`.

**Reihenfolge:** Recurring-Endpoint → LLM-Kategorisierung + Backfill →
Focus-Kategorien-Endpoints → Tab-Leiste + Konto-Umschalter →
Übersicht-Tab (Hero/Quickstats/Verträge-Vorschau) → Verträge-Tab →
Desktop-Zweispalter → Live-Test (Mobile+Desktop-Breiten,
Atem-Abstand-Kontrolle) → Protokoll/CHANGELOG/Help → pytest → Commit.
