# Restoring Yorik from a backup

Backups produced by `POST /api/backup/run` (or the scheduled run) are
encrypted with the operator's passphrase. They contain:

- Yorik's main + docs Postgres schemas (`yorik_postgres.sql.gz`,
  `yorik_postgres_docs.sql.gz`).
- Each tenant's Postgres database (`tenants/<name>/postgres.sql.gz`).
- Each tenant's manifest + bearer token (`tenants/<name>/manifest.env`,
  `tenants/<name>/internal_token`).
- `data/.credential_key` — the Fernet master that decrypts every
  stored connector token. Lose this and stored API keys become
  permanently undecryptable.
- `data/documents/` — locally-uploaded Yorik documents.
- `briefings/` — generated PDFs + the source tree.

The backup does **not** include Immich's photo library, Paperless's
database / media, or `/etc/caddy/Caddyfile`. Those are restored
separately (see "Manual recovery" below).

## Automated restore

> Pre-requisites: same Yorik install layout as the snapshot was taken
> from, `supabase-db` container running, and you are logged in as the
> install user (`yorik` on the standard self-host).

```bash
cd ~/yorikai/yorik-ai
bash scripts/restore-from-snapshot.sh /path/to/snapshot.tar.gz.age
# Prompts for the passphrase if not piped on stdin.
```

The script:

1. Verifies the snapshot decrypts + integrity-checks cleanly (refuses
   to proceed otherwise).
2. Stops `yorik.service` and every `yorik-tenant@*.service`.
3. `DROP SCHEMA … CASCADE` on the host's `public`, `yorik`, `docs`
   schemas, then pipes the dumps back through `psql`.
4. For each tenant in the bundle: `DROP DATABASE yorik_tenant_<name>`,
   `CREATE DATABASE …`, replay the dump.
5. Restores `.credential_key`, `data/documents/`, `briefings/`, and
   each tenant's `manifest.env` + `internal_token`.
6. Restarts `yorik.service`. Tenants are **not** auto-restarted — see
   step 3 below so you can confirm each tenant came back cleanly
   before exposing the subdomain.

After the script finishes:

```bash
# 1. Start each tenant. The systemd template is already installed.
for t in $(ls data/tenants); do
  sudo systemctl start yorik-tenant@$t.service
done

# 2. Reload Caddy only if the /etc/caddy/Caddyfile lost the per-tenant
# `import infra/caddy/tenants/*.caddy` block — the snippets themselves
# get regenerated by create-tenant.sh, NOT the restore.
sudo systemctl reload caddy

# 3. Smoke-test
curl -sS https://wir.winiecki.ai/api/health
for t in $(ls data/tenants); do
  curl -sS https://$t.wir.winiecki.ai/api/health
done
```

## Manual recovery (what the restore script does NOT cover)

### Immich photo library

Immich's photos and Postgres live in docker volumes (`yorik-ai_immich_postgres`,
`yorik-ai_immich_model_cache`) + a bind mount at `data/immich_library`.
The backup contains an `immich_library` entry **only** when
`include_photos=true` was set in the backup config — Immich
libraries are often huge (>50 GB), so the default is off.

To restore Immich:

1. Decrypt + extract the snapshot manually:
   ```bash
   age -d -p snapshot.tar.gz.age | tar -xzf - -C /tmp/yorik-extracted
   ```
2. Stop Immich: `docker compose stop immich-server immich-machine-learning`
3. Replace the photo library directory:
   ```bash
   sudo rsync -a --delete /tmp/yorik-extracted/immich_library/ data/immich_library/
   ```
4. Restore Immich Postgres: similar `pg_restore` pattern as above, but
   against the `yorik-immich-postgres` container.
5. `docker compose start immich-server immich-machine-learning`

### Paperless

Paperless's database + media live in named docker volumes. The backup
contains `paperless_data` + `paperless_media` entries **only** when
`include_paperless=true` was set. Restore steps mirror the Immich
flow: stop the paperless containers, replace the volume contents,
restart.

### Caddy configuration

`/etc/caddy/Caddyfile` is not in the snapshot. Per-tenant snippets at
`infra/caddy/tenants/<name>.caddy` ARE in the repo and get re-emitted
by `create-tenant.sh`. If the operator changed the master Caddyfile
(e.g. added a custom `acme_dns` block), back it up via `/etc/` rsync
separately.

## Verifying a snapshot without restoring

Useful for "does my passphrase still work?" or "is this backup
corrupt?" without touching live data:

```bash
cd ~/yorikai/yorik-ai
source venv/bin/activate
PYTHONPATH=. python3 -c "
from pathlib import Path
from backend.backup import verify_snapshot
r = verify_snapshot(Path('snapshot.tar.gz.age'), 'YOUR-PASSPHRASE')
print(r['summary'])
for c in r['checks']:
    mark = 'OK' if c['ok'] else 'FAIL'
    print(f'  [{mark}] {c[\"name\"]}: {c[\"detail\"]}')
"
```

Runs the same decrypt + integrity + manifest checks the automated
restore runs as its first step, but only writes to a tmpdir.

## Recovery time expectations

For the reference family-tier install (≤6 tenants, ≤2 GB docs):

| Step                       | Time   |
|----------------------------|--------|
| Decrypt + extract          | 5–30s  |
| Restore Yorik main + docs  | 10–60s |
| Restore each tenant DB     | 5–20s  |
| Restore credential_key + files | <5s |
| **Total RTO**              | **1–3 min** |

Immich and Paperless restores can dominate this — a 50 GB Immich
library takes ~10 min over USB-C to a hot SSD.
